# 审批材料预检助手（Expense Precheck）

> 员工提交报销申请时，在材料进入审批流**之前**先自动检查一遍：该有的发票齐不齐、金额对不对得上、发票有没有重复、事由和费用科目有没有矛盾，然后直接告诉他**缺什么、差多少、怎么改**。
>
> **它不做审批决定。** 批准或拒绝始终由人完成——它只负责把"因为少一张发票被退回三次"这类来回踢球的浪费消掉。

---

## 它解决什么问题

真实场景里最常见的三句对话：

| 员工 | 财务 |
|---|---|
| "我这个报销什么时候能到账？" | "你发票少了一张，退回。" |
| "哪张少了？" | "差旅只交了机票，没有住宿票。" |
| "……那我明天重新提一次。" | — |

材料齐不齐、金额对不对，是**提交后**才被发现的，于是每次都要往返一两天。这个工具把这一步提到**提交前 1 秒**：

```
🔴 差旅报销缺少住宿票据
   证据：已上传 1 份：交通·机票_1012.pdf
   怎么改：请补上住宿发票；如果是当天往返不需要住宿，请在事由里说明

🔴 发票号 25310000000012345678 重复提交 2 次（450.00 元）
   涉及附件：机票_1012.pdf、机票_1012_重复上传.pdf

🟡 AI 指出：事由为办公用品采购，明细却是护肤品，开票方为化妆品公司
   怎么改：请核实实际采购内容，如为护肤品应改列福利等相应类别
```

## 快速开始

**环境**：JDK 17+、Maven 3.9+（不需要数据库、不需要 Node）

```bash
# 1. 编译并打成一个可运行的 jar
mvn clean package

# 2. 启动
java -jar target/expense-precheck-0.0.1-SNAPSHOT.jar

# 3. 打开浏览器
#    http://localhost:8090
```

第一次用建议直接点页面上的 **「没有发票？载入样例数据」**——不用准备任何文件就能看到完整效果。

想启用 AI 语义检查（可选），先设置环境变量再启动：

```bash
# Windows CMD
set PRECHECK_AI_KEY=sk-你的key
# PowerShell
$env:PRECHECK_AI_KEY="sk-你的key"
# 不想用 AI：不设就行，系统会自动降级成纯规则
```

默认接 DeepSeek（OpenAI 兼容接口），可在 `application.yml` 的 `precheck.ai.*` 里换成别家。

## 怎么用

1. 填申请单（申请人、费用类别、申报金额、事由、起止日期）
2. 填费用明细（几条都行，删改随意）
3. 上传电子发票 PDF（可多选）
4. 点「开始预检」

几处刻意的设计：

- **每张发票旁边有「手工金额」输入框。** 解析失败或识别错了，填个数字照样能跑完整流程——这是真实场景的兜底，不是补丁。
- **结果分三栏**：必须补（阻断提交）/ 建议核对 / 提示。只有"确实没法审"的问题才阻断。
- **每条都带证据**：哪张附件、哪个数字，指得出来员工才服。

## 检查规则

| 编号 | 检查什么 | 判定方式 | 级别 |
|---|---|---|---|
| R2 | 必备附件类型齐全 | 按费用类别查必备票据（差旅=交通+住宿，其他=发票）；**算得出或说清原因的可以降级**，见下 | 阻断 / 建议核对 |
| R3 | 申报金额 = 明细合计 | 两者的差超过容差 | 阻断 |
| R4 | 发票合计 = 明细合计 | **按发票号去重后**再比 | 阻断 |
| R5 | 同一张发票不能报两次 | 发票号分组，出现多次即重复 | 阻断 |
| A1 | 事由与费用类别是否相符 | 大模型做语义判断 | 建议核对（永不阻断） |

### R2 的三种情形（缺票不等于一定卡人）

"差旅必须有住宿票"这条规则，遇到"当天往返"就会变成机械卡人。所以缺票时分三种处理：

| 情形 | 怎么判断 | 结果 |
|---|---|---|
| 当天往返 | **起止日期是同一天** —— 表单里已有的事实，直接算，不问员工 | 一条提示，不阻断 |
| 跨天但确实没住宿 | 员工在「票据例外说明」里选了原因（客户安排 / 自驾 / 其他）**并写了情况** | 降为「建议核对」，交审批人核实 |
| 其余 | 缺票且没有任何说明 | 阻断，并明确告诉员工怎么把这一项消掉 |

**为什么不读事由里的"当天往返"四个字**：那等于教员工写一句万金油话术绕过检查，正是这个工具最该避免的事。能算的用日期算，算不出来的要求结构化声明 + 文字说明，两条腿都不能少——只勾下拉不写字，声明不成立。

两条关键取舍：

- **R4 比对前先按发票号去重。** 否则"传重了"这一个错误会被放大成"差 470 元"，员工会觉得系统在找茬。去重后差额指向真正的问题。
- **AI 的结论最高只到"建议核对"。** 语义判断有误判可能，不能挡住员工提交；而"金额差 31 元"是硬事实，才配阻断。

## 设计要点

**1. 解析与校验彻底解耦，中间只传一份 `Facts`（事实集）**

```
材料 → 解析层 → Facts JSON → 硬规则（代码）+ 软规则（LLM）→ 补正清单
```

好处很实在：规则可以脱离真实文件单测（手写一份 Facts 就能断言"应该报差 20 元"），将来换 OCR 或接电子发票查验接口，校验层一行都不用改。

**2. 能算的用代码算，不能算的才给模型**

金额加总、发票张数、查重是确定性的，代码 100% 准、零成本、可单测。让模型算加法，它错得你看不出来。只有"事由和科目对不对得上"这种才需要语义理解。

**3. 金额一律 `BigDecimal` + 容差**

用 `double` 会把 1130 变成 1129.9999999；比较永远用 `compareTo`（`new BigDecimal("1130.0").equals(new BigDecimal("1130.00"))` 是 `false`！）。容差默认 1 分钱，可配置。

**4. 失败一律降级，绝不假装通过**

| 情况 | 行为 |
|---|---|
| 没配 API Key | 静默跳过语义检查 |
| 模型超时/报错 | 提示"本次语义检查未完成"，硬规则照跑 |
| 模型返回乱码 | 提示"无法解析"，不崩 |
| 某条规则抛异常 | 引擎兜住，降级成一条提醒，不影响其他规则 |
| PDF 读不出文字 | 提示"请手工填金额"，不阻断流程 |

**最危险的做法是"假装通过"**——那会让员工带着问题提交，比报错糟糕得多。

## 规则可配置（不用改代码）

`src/main/resources/rules.yml` 就是"公司制度"的落地形式：

```yaml
precheck:
  rules:
    amount-tolerance: 0.01

    required-attachments:
      - category: 差旅
        required: [TRAVEL, HOTEL]
      - category: 默认
        required: [INVOICE]

    ticket-keywords:
      HOTEL: [住宿服务, 住宿费, 酒店, 宾馆, 民宿]
      TRAVEL: [运输服务, 客运, 机票, 火车票, 滴滴]
```

**想让客户自己改规则、又不想重新打包**：把 `rules.yml` 放到 jar 同级目录，重启即生效（`spring.config.import` 会覆盖 jar 内的默认值）。

> ⚠️ 踩过的坑：`required-attachments` 最初写成「中文当 key」的 map（`差旅: [...]`），Spring 配置绑定**静默失效**——不报错、不警告，就是行为不变。改成「列表 + category 字段」，中文只出现在值里才正常。
> **结论：YAML 里中文可以当值，别当 key。**

## 接口

只有两个，够用。

**`POST /api/precheck`** —— 提交预检（multipart）

| 分片 | 内容 |
|---|---|
| `payload` | 申请单 JSON（`type` / `applicant` / `declaredAmount` / `reason` / `category` / `startDate` / `endDate` / `lineItems` / `overrides`） |
| `files` | 发票 PDF，可多个 |

**`GET /api/precheck/sample`** —— 返回内置样例的预检结果（页面上「载入样例数据」用的就是它）

返回结构：

```json
{
  "passed": false,
  "blockCount": 2, "warnCount": 0, "infoCount": 0,
  "summary": "发现 2 个必须补的问题。补齐后再提交，可以少跑一趟。",
  "findings": [
    {
      "ruleId": "R4_INVOICE_TOTAL",
      "level": "BLOCK",
      "message": "发票合计 1150.00 元，与明细合计 1130.00 元不一致，相差 20.00 元",
      "evidence": "计入 2 张发票：机票_1012.pdf 450.00 元、住宿_1013.pdf 700.00 元；重复上传已排除 1 张",
      "suggestion": "请逐项核对：发票金额多于明细，可能漏记了某笔费用的明细",
      "source": "RULE"
    }
  ],
  "attachments": [ ... ],
  "parseWarnings": [ ... ]
}
```

## 项目结构

```
src/main/java/com/precheck/
├── ExpensePrecheckApplication.java
├── facts/          Facts              事实集，全套系统的内部契约
├── parse/          PDF 解析：抽文本 → 抽字段 → 判票型
├── rule/           CheckRule 接口、Finding、Level、引擎、报告
│   └── impl/       R2 / R3 / R4 / R5 / A1 五条规则
├── ai/             AiClient 接口 + DeepSeek 实现（可替换）
├── config/         规则配置绑定（rules.yml）
├── support/        Money（金额必须从这里走）
├── service/        串起整条链路
└── web/            两个接口 + 请求/响应模型

src/main/resources/
├── static/index.html   单页前端（原生 HTML + fetch，零构建）
├── rules.yml           规则配置
├── application.yml
└── samples/            样例数据
```

**加一条新规则 = 在 `rule/impl/` 新增一个类 + 打 `@Component`**，引擎不用改、其他规则不用改。

## 技术栈

| 用途 | 选型 |
|---|---|
| 语言 / 框架 | Java 17 + Spring Boot 4.1.1 |
| PDF 文本抽取 | Apache PDFBox 3.0.5 |
| JSON | Jackson 3（Boot 4 已内置） |
| AI | DeepSeek（OpenAI 兼容接口），用 JDK 自带 HttpClient 直连 |
| 前端 | 原生 HTML + fetch，无框架无构建 |

> 两个 Boot 4 的坑，抄网上代码时容易撞：
> 1. web 依赖改名 `spring-boot-starter-web` → **`spring-boot-starter-webmvc`**（测试包同理 `-webmvc-test`）。
> 2. Boot 4 已切到 **Jackson 3**，包名从 `com.fasterxml.jackson.*` 变成 `tools.jackson.*`。

## 测试

```bash
mvn test        # 25 个用例（其中一个真发票用例默认跳过，见下）
```

真发票的端到端用例不进仓库（含个人信息），默认跳过。想跑就指定一张自己的电子发票：

```bash
mvn test -Dinvoice.sample="C:/path/to/发票.pdf"
```

测试策略上有两点特意为之：

- **AI 规则用"假模型"测**（`StubAi`），覆盖正常/可疑/代码块包裹/乱码/无响应/未配置六种返回，不联网、不花 token、结果稳定。
- **真实 PDF 的测试用 `assumeTrue`**：本机有这张样例发票就跑，没有就跳过，换台机器不会因为"文件不存在"而失败。

## 已知限制（诚实清单）

| 限制 | 说明 |
|---|---|
| 多页 PDF 只认第一页 | 多张发票合并成一个 PDF 时，目前只解析第一页 |
| 只支持电子发票 | 依赖 PDF 的文字层；拍照、扫描件读不出来（会走"请手工填金额"） |
| 无数据库 | 一次请求算完就返回，不留历史，无法统计"最常见的退单原因" |
| 无登录与权限 | 预检只是提交前的一层检查，不需要用户体系 |
| 只做报销 | 采购、差旅申请、用章等场景未实现 |
| 金额只做总额比对 | 尚未做"某一笔明细对应哪张发票"的逐条匹配 |
| 规则改动需重启 | 没有热更新 |
